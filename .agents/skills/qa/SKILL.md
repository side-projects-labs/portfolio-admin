# QA

## 범위 파악

`git status`, `git diff` (브랜치 단위면 `git diff origin/master...HEAD`)로 변경 파일과 영향 받는 영역(`src/app`, `src/components`, `src/lib`, `src/hooks`, `src/middleware.ts`)을 확인한다.

브랜치 비교 전 `git fetch origin`을 수행하고 기준 SHA를 기록합니다. 이슈 본문·댓글 또는 사용자 요구의 기대 동작과 제약을 먼저 확인합니다. 실제 데이터 생산자(portfolio-api 응답, Supabase)·변환·저장/캐시(SWR, zustand, 쿠키)·소비자와 공통 모델의 소유권을 따라 영향 범위를 정합니다.

## 1단계: 정적 검증

PR CI(`.github/workflows/ci-deploy.yml`의 `Lint, type-check, and test`)와 같은 명령을 사용한다. 로컬 QA는 빌드를 추가로 확인한다.

```bash
pnpm lint
pnpm type-check
pnpm build
```

- `pnpm lint`는 `next lint`다. 자동 수정이 필요하면 사용자가 요청했을 때만 `pnpm lint:fix`를 쓰고 수정된 파일을 리포트에 명시한다
- `pnpm type-check`가 `.next/types/validator.ts` 같은 git이 무시하는 빌드 캐시의 오래된 경로 때문에만 실패하면, 소스 오류와 구분해 기록한다. 소스에 오류가 있는 것으로 보고하지 않는다
- `pnpm build`는 외부 API와 환경변수가 필요할 수 있다. 실행하지 못했으면 이유와 함께 "생략"으로 적는다

## 2단계: 테스트

```bash
pnpm test
pnpm test src/lib/api.test.ts   # 변경 경로만
```

- 변경된 `src/**` 로직에 대응 테스트가 없으면 "테스트 누락"으로 기록한다 (필요 시 `tdd` 스킬 제안)
- 인증·리디렉션 변경은 인접한 로그인 테스트(`src/middleware.test.ts`, `src/components/ui/login-form.test.tsx`, `login-menu.test.tsx`)를 함께 확인한다
- 기존부터 실패하던 테스트는 이번 변경과 구분해 기록한다

## 3단계: 화면 / API 확인

개발 서버는 띄우지 않는다. 사용자가 이미 `pnpm dev`(5001 포트) 또는 `pnpm dev:https`를 실행 중이거나 컨테이너로 띄운 경우에만 확인한다.

- UI 변경: 영향 받는 페이지를 브라우저에서 열고, 주요 동작(클릭, 입력, 빈 상태, 다크 모드, 반응형)을 확인한다
- 로그인·미들웨어 변경: 쿠키 없음, 거절된 토큰, 인증 서버 장애 상태에서 `/login`과 보호된 화면의 응답을 확인한다. 쿠키·토큰 값은 출력하지 않는다
- `src/app/api/*` 변경: 떠 있는 서버에만 요청한다. middleware가 API 경로를 제외하므로 화면 보호만으로 API 권한이 검증됐다고 판단하지 않는다. 비밀값과 토큰은 출력하지 않는다
- 서버가 없으면 "생략 (개발 서버 없음)"으로 적는다

## 4단계: 코드 리뷰

`review` 스킬(`.agents/skills/review/SKILL.md`)을 staged/branch/local 중 실제 변경 범위에 맞게 실행하고 발견 사항을 리포트에 그대로 옮깁니다. 미커밋 변경은 local 모드에서 staged·unstaged·관련 untracked 내용을 구분합니다. 일반 QA는 PR 댓글을 자동 작성하지 않습니다.

불변조건과 관련 시나리오를 확인·위반·미확인·해당 없음으로 구분합니다. 설정 변경도 모듈 해석·빌드·런타임·공개 노출 경계를 검토합니다. 테스트 통과만으로 서비스 전체를 확인했다고 쓰지 않습니다. 중요한 미확인은 검증 보류에 해당하는 차단 사항으로 기록하고, 수정 후 최신 상태에서 목적·변경·주변 영향·검증을 재검토합니다.

차단 발견이나 중요한 검증 보류가 있으면 QA 결과는 실패로 기록합니다.

## 리포트 형식

```markdown
## QA 결과: <통과 | 조건부 통과 | 실패>

| 항목          | 결과       | 비고                |
| ------------- | ---------- | ------------------- |
| Lint          | ✅/❌      |                     |
| 타입 체크     | ✅/❌      |                     |
| 빌드          | ✅/❌/생략 |                     |
| 단위 테스트   | ✅/❌      | n passed / m failed |
| 화면/API 확인 | ✅/❌/생략 |                     |

### 발견 사항

- 🔴 반드시 수정: <파일:라인 - 내용>
- 🟡 권장: <내용>
- 🟢 참고: <내용>

### 다음 단계

<수정 필요 항목 또는 commit/pr 진행 제안>

### 불변조건과 미확인 사항

- <관련 시나리오의 기대 결과, 확인 상태와 근거를 적습니다.>
- <실행하지 못한 검증, 판정 영향과 필요한 최소 추가 검증을 적습니다.>
```

발견 사항과 생략 이유처럼 근거를 남기는 문장은 `~습니다`로 끝낸다. 발견 사항은 보고만 하고, 수정은 사용자가 요청하거나 명백한 린트 자동수정에 한해 진행한다.
